## 一、事务隔离、MVCC 与长事务

### 1. 串行化

- **原记忆点：串行化会通过加锁，让事务尽量按顺序执行。**
- **通俗理解：** 大家不要同时抢着操作，尽量一个一个来，所以并发能力会下降。

> 这一条原笔记写的是“为所有 SQL 加入行级锁”，表述比较绝对，复习时建议重点记住“通过更严格的加锁来减少并发冲突”这一层意思。

### 2. MVCC：读已提交（RC）和可重复读（RR）的区别

- **核心区别：Read View 的生成时机不同。**
- **RC：** 每次执行快照读的 `SELECT`，都会看一个新的 Read View。
- **RR：** 第一次快照读建立 Read View 后，后续快照读继续沿用它。

**通俗理解：**

- RC 像“每次查询都重新拍一张照片”，所以后一次查询可能看到别人刚提交的新数据。
- RR 像“事务里一直看同一张照片”，所以前后两次快照读看到的数据更稳定。

### 3. 可重复读与快照读

- 在 **RR 隔离级别** 下，如果前后两次都是快照读，就不会出现前后两次读取同一条数据却结果不一致的问题。

**通俗理解：** 事务第一次看到的是哪个版本，后面继续按照这个版本看，因此不会因为别人中途提交修改，就突然看到另一个结果。

### 4. 为什么要注意长事务

- 锁通常要等到事务 `COMMIT` 后才释放。
- 长事务会让 Undo Log 长时间不能清理，导致日志堆积、占用更多存储空间。
- 长事务回滚时，需要处理的内容更多，因此回滚时间也可能更长。
- 长事务执行时间过长，还容易造成主从延迟。

**通俗理解：** 一个事务一直不结束，就像一个人长时间占着位置不走：锁不释放、旧版本不能及时清理，后面的工作也容易被拖慢。

### 5. MDL 锁与创建索引

- 创建索引时会涉及 **MDL（Metadata Lock，元数据锁）**。
- 如果同时还有其他事务在访问这张表，就可能因为 MDL 锁之间的等待产生阻塞。

**通俗理解：** 一个操作想“改表的结构”，另一个操作还在“使用这张表”，两边可能互相等，因此 DDL 操作要注意长事务和并发访问。

## 二、InnoDB 的行级锁

### 1. Record Lock（记录锁）

- **作用：锁住一条已经存在的索引记录。**
- 可以避免其他事务同时对这条记录进行删除或更新。

**通俗理解：** 只锁“这个人”，不管旁边的空位置。

### 2. Gap Lock（间隙锁）

- **作用：锁住两条索引记录之间的间隙。**
- 主要避免其他事务往这个间隙中插入新记录。

**通俗理解：** 不锁已经存在的人，而是把两个记录中间的“空位”占住，不让别人往里面塞新数据。

### 3. Next-Key Lock（临键锁）

- **Next-Key Lock = Record Lock + Gap Lock。**
- 既锁住记录，也锁住记录前面的间隙。

**通俗理解：** “这个人”和“他前面的空位”一起锁。

### 4. Insert Intention Lock（插入意向锁）

- 当事务准备往某个间隙中插入记录时，会产生插入意向锁。
- 如果该位置已经存在阻止插入的间隙锁，那么插入操作就需要等待。

**通俗理解：** 相当于事务先表示：“我要往这个空位里插一条数据。”如果别人已经把这个空位锁住，它就只能等。

### 5. 间隙锁为什么能防止幻读

- 其他事务想往被保护的间隙中插入数据时，会因为锁冲突而等待。
- 因此当前事务执行期间，这个范围内不会突然插入新的记录。

**通俗理解：** 第一次查的时候这个范围里没有 `15`，把中间空位锁住后，别人就不能突然插入 `15`，这样下一次再查就不会凭空多出一条记录。

### 6. `UPDATE` 没有带 `WHERE`

```sql
UPDATE table_name SET ...;
```

- **RR：** 会对扫描到的记录及相关范围加锁，原笔记重点记忆为 **Next-Key Lock**。
- **RC：** 原笔记重点记忆为 **Record Lock**。

**通俗理解：** 没有 `WHERE` 就意味着需要处理整张表中的记录，锁的范围会非常大，所以这类 SQL 风险很高。

## 三、死锁排查与避免

### 1. 如何排查死锁

使用：

```sql
SHOW ENGINE INNODB STATUS;
```

- 用它查看 InnoDB 最近的死锁相关信息。

### 2. 如何尽量避免死锁

原笔记核心点：

- 锁超时
- 锁检测
- 减少锁范围
- 减少锁持有时间
- 减少不必要的间隙锁

**最值得记的两个方向：**

> **少锁一点 + 少锁一会儿。**

也就是尽量缩小锁的范围，同时让事务尽快执行完并提交。

## 四、MySQL 三大日志

### 1. 三大日志分别做什么

#### Undo Log

- **核心：回滚 + MVCC。**

**通俗理解：** 负责“往回找”。事务要回滚，或者 MVCC 要找旧版本的数据，都需要它。

#### Redo Log

- **核心：掉电恢复 + 持久性。**

**通俗理解：** 已经答应你“事务提交成功”了，即使真正的数据页还没完全写回磁盘，也可以靠 Redo Log 在宕机后把修改恢复出来。

#### Binlog

- 记录表结构变化和表数据修改。
- 主要用于 **数据备份和主从复制**。

**通俗理解：** 更像是 MySQL 记录“数据库发生过哪些修改”的日志，可以把这些修改传给从库继续执行。

---

### 2. Binlog 的三种格式

- `STATEMENT`
- `ROW`
- `MIXED`

这一部分按原笔记记住三种模式即可。

---

### 3. Redo Log 和 Binlog 的记忆区别

#### Redo Log

- 属于 InnoDB。
- 重点记录还没有完全刷入数据文件的数据页修改，用于崩溃恢复。

#### Binlog

- 记录数据库中的修改操作。
- 主要服务于备份和主从复制。

**通俗区分：**

- **Redo Log：更关心“数据库宕机后怎么把已经提交的数据救回来”。**
- **Binlog：更关心“数据库发生了什么修改，怎么备份、怎么复制给从库”。**

## 五、两阶段提交

### 1. 为什么需要两阶段提交

原笔记场景：

```text
Redo Log 已经刷盘
↓
MySQL 突然宕机
↓
Binlog 还没来得及写入磁盘
```

如果两份日志状态对不上，就会影响后续恢复和主从复制的一致性。

### 2. 两个阶段

#### 第一阶段：Prepare

- Redo Log 先进入 `prepare` 状态并刷盘。

**通俗理解：** 先把 Redo Log “保险存好”，但暂时不宣布整个事务彻底完成。

#### 第二阶段：Commit

- Binlog 刷盘完成后，再把 Redo Log 改成 `commit` 状态。

**通俗理解：** 等 Binlog 也确认记录好了，才最终宣布：“这个事务完整提交成功。”

## 六、Redo Log 刷盘参数 0 / 1 / 2

### 参数 0

- Redo Log 先留在 Redo Log Buffer 中。
- **特点：写入性能较好，但安全性较低。**

### 参数 1

- 将 Redo Log Buffer 中的 Redo Log 持久化到磁盘。
- **特点：安全性高，但刷盘更频繁。**

### 参数 2

- 将 Redo Log Buffer 中的数据写到操作系统的 Page Cache。

**通俗记忆：**

```text
0：先留在 MySQL 内存里
1：直接要求落到磁盘
2：先交给操作系统缓存
```

原笔记重点：

> **0 更偏性能，1 更偏安全。**

## 八、MySQL 主从复制

### 1. 主从复制流程

可以按这条链路记：

```text
从库连接主库
↓
主库 Binlog Dump 线程传递 Binlog
↓
从库把内容写入 Relay Log（中继日志）
↓
回放线程读取 Relay Log
↓
在从库重新执行这些修改
↓
最终实现主从数据同步
```

**通俗理解：** 主库把自己的“修改记录”告诉从库，从库先记下来，再按照记录重新做一遍。

### 2. 复制模式

原笔记三种：

- 同步复制
- 异步复制
- 半同步复制

## 九、读写分离与主库切换

### 1. MyCat

- 可以独立部署代理中间件 **MyCat** 来实现读写分离。

**通俗理解：** 应用不用自己判断请求应该去主库还是从库，由中间件帮忙把不同请求分发到对应数据库。

### 2. MHA

- 原笔记重点：**用于主库故障后的主库切换。**

**通俗理解：** 主库挂了以后，需要把备用节点顶上来继续当主库，MHA 负责这类主库切换工作。

## 十、分表与分库

### 1. 分表

- 原笔记：数据量达到较大规模时，可以考虑分表，减少单表的数据量和查询压力。

**通俗理解：** 一张表太大，就把它拆成几张小表，避免每次都面对一张特别大的表。

### 2. 分库

- 当单台 MySQL 扛不住高并发流量时，可以考虑分库。
- 把并发请求分散到多台 MySQL 实例上。

**通俗理解：**

```text
一台 MySQL 扛所有请求
        ↓
       太累
        ↓
拆到多台 MySQL
        ↓
大家一起分担请求
```
