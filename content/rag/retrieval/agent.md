# 一、如何设计 Agent 评测流程

## 第一步：明确业务目标与任务边界

在设计评测流程之前，先回答以下问题：

1. Agent 的核心任务是什么？
2. 什么情况代表任务成功？
3. 什么情况代表任务失败？
4. 失败会造成什么代价？
5. Agent 是否会执行具有真实副作用的操作？

所谓“真实副作用”，是指 Agent 的行为会直接改变外部世界，例如：

- 发送邮件；
- 修改数据库；
- 创建或删除文件；
- 支付款项；
- 提交订单；
- 修改线上配置。

任务的风险越高，评测门槛、权限控制和审批机制就应该越严格。

## 第二步：拆解关键能力

不要只评价 Agent 最终回答得“好不好”，还要把完整任务拆成多个能力层分别评估。

一个典型 Agent 通常包含以下能力：

1. **输入理解**：是否正确理解用户意图、条件和限制；
2. **规划（Planning）**：是否能将复杂任务拆成合理步骤；
3. **检索（Retrieval）**：是否能找到相关信息并正确放入上下文；
4. **工具选择**：是否选择了正确的工具；
5. **参数生成**：是否填写了正确、完整且安全的工具参数；
6. **目标定位**：是否找到了正确的文件、用户、数据或操作对象；
7. **内容生成**：最终输出是否准确、完整、清晰；
8. **审批与安全控制**：高风险操作是否触发了审批、确认或策略检查。

> 分层评测的价值：即使最终任务失败，也能判断问题发生在理解、规划、检索、工具调用还是安全控制环节。

## 第三步：构造分层数据集

评测数据集至少应包含以下四类 Case：

| 数据类型 | 作用 | 示例 |
|---|---|---|
| 核心高频 Case | 验证主要业务是否稳定 | 用户最常使用的任务 |
| 历史失败 Case | 防止旧问题再次出现 | 线上事故、Bad Case |
| 边界 Case | 验证极端条件下的表现 | 超长输入、缺失参数、模糊指令 |
| 对抗与风险 Case | 验证安全能力 | Prompt Injection、越权调用、危险参数 |

其中，历史失败 Case 在修复后应进入固定回归集，避免后续版本重新引入同类问题。

## 第四步：选择评价器

评价器可以分为三类：

### 1. 规则评价器

只要能够用确定性规则判断，就优先使用规则。

优点：

- 稳定；
- 成本低；
- 速度快；
- 可解释性强；
- 容易用于自动化门禁。

适用场景：

- JSON Schema 是否通过；
- 工具名称是否正确；
- 参数是否完整；
- 是否调用了禁止工具；
- 输出是否包含必填字段；
- 是否超过 Step、Token 或 Timeout Budget。

### 2. 大模型评价器

当问题难以通过固定规则判断时，可以使用大模型进行评价，例如：

- 回答是否完整；
- 规划是否合理；
- 引用是否支持结论；
- 最终结果是否符合用户意图。

使用大模型评价器时，应尽量明确：

- 评分维度；
- 评分标准；
- 评分区间；
- 示例答案；
- 不同分数对应的判断条件。

### 3. 人工评价

对于高风险、重要或难以稳定自动判断的任务，应升级为人工评价。

推荐顺序：

> **能用规则就用规则；规则无法覆盖时使用大模型；关键问题再升级到人工判断。**

## 第五步：建立 Baseline 与发布门禁

### Baseline 是什么？

Baseline 是当前稳定版本在固定评测集上的表现，用于比较新版本是否真的变好。

Baseline 可以包含：

- 总任务成功率；
- 各能力层成功率；
- 高风险 Case 通过率；
- 平均 Step 数；
- P50、P95 延迟；
- 每成功任务成本；
- 工具调用失败率；
- 安全事件数量。

### 门禁是什么？

门禁是发布前必须满足的最低标准。

不仅要规定“哪些指标需要提升”，还应明确：

- 哪些指标允许小幅下降；
- 哪些指标绝对不能下降；
- 哪些 Case 一旦失败就属于 Blocker；
- 哪些安全问题必须阻断发布；
- 超过什么成本或延迟阈值不能上线。

例如：

- 核心任务成功率不得低于 Baseline；
- 高风险 Case 必须全部通过；
- 不得新增越权工具调用；
- P95 延迟不得超过门禁阈值；
- 每成功任务成本不得显著上升。

## 第六步：把评测结果接回开发循环

评测不是一次性验收，而应该形成持续开发闭环：

```text
修改 Prompt / Model / Tool / Workflow
                ↓
运行离线评测
                ↓
分析失败样本与 Trace
                ↓
定位根因并修复
                ↓
重新执行回归测试
                ↓
通过门禁后进入灰度发布
```

# 二、在线评测与离线评测

## 1. 在线评测的主要手段

### 实时指标监控

持续观察：

- 成功率；
- 错误率；
- Step 数；
- 工具调用分布；
- P50、P95、P99 延迟；
- Token 消耗；
- 每成功任务成本；
- 安全事件数量。

### 线上抽样复核

从真实请求中抽取部分样本，由人工或评价器复核任务质量。

### Shadow 对比

将线上真实请求复制给新版本运行，但新版本的结果不真正返回给用户，也不产生真实副作用。

作用：

- 观察新旧版本行为差异；
- 提前发现错误工具调用；
- 比较成本、延迟和 Step 数；
- 降低直接上线风险。

### SBS 比较

SBS 即 Side-by-Side，将两个版本的结果放在一起，由评价器或人工判断哪个更好。

### 小流量 A/B 测试

让少量真实用户分别使用不同版本，比较真实业务指标。

### 线上异常检测

识别以下异常：

- Step 数突然增多；
- 某工具调用频率异常；
- 成本快速上涨；
- P95 延迟恶化；
- 安全事件增加；
- 某类任务成功率下降。

## 2. 在线与离线评测如何闭环

推荐闭环如下：

```text
在线发现问题
    ↓
抽取失败样本
    ↓
清洗与标注
    ↓
加入离线失败集或回归集
    ↓
重新运行离线评测
    ↓
修复问题
    ↓
通过门禁后灰度上线
```

一句话理解：

> **在线评测负责发现真实世界的问题，离线评测负责在可控环境中修复和验证问题。**

# 三、可观测性：Metric、Trace 与 Log

## 1. Metric：看整体趋势

Metric 用于观察系统整体是否变好或变坏，适合展示在 Dashboard 中。

常见指标：

- 成功率；
- 错误率；
- P50、P95、P99 延迟；
- 平均 Step 数；
- Token 消耗；
- 工具调用成功率；
- 每成功任务成本。

例如：

> 某个工具的 P95 延迟本周上升了 30%。

Metric 能告诉我们“系统出现了趋势性问题”，但通常不能直接解释某一次请求为什么失败。

## 2. Trace：看单次请求的完整链路

Trace 用于查看一个请求经过了哪些节点，以及每一步之间的因果关系。

一个 Trace 可能包含：

```text
用户请求
→ 意图识别
→ 任务规划
→ 检索
→ 模型决策
→ 工具调用
→ 审批
→ 最终生成
→ 返回用户
```

通过 Trace 可以判断：

- Agent 为什么选择了某个工具；
- 是否出现循环调用；
- 哪一步耗时最长；
- 哪个节点跳过了 Policy Check；
- 错误参数从哪里产生；
- 最终结果受到哪条上下文影响。

## 3. Log：保存细节和原始证据

Log 负责记录具体事件和原始信息，例如：

- 错误堆栈；
- 工具返回值；
- 参数校验失败原因；
- 外部服务响应；
- 重试与超时信息；
- 审批记录。

## 4. 三者的区别

| 类型 | 主要作用 | 回答的问题 |
|---|---|---|
| Metric | 查看趋势 | 系统整体是否变差？ |
| Trace | 查看完整链路 | 这次请求为什么失败？ |
| Log | 保存原始细节 | 具体报错和证据是什么？ |

## 5. Replay：问题回放

常见回放方式包括：

1. **输入回放**：使用相同输入重新运行；
2. **Trace 回放**：按照原调用链重现过程；
3. **环境快照回放**：恢复当时的模型、配置、数据和工具环境；
4. **Shadow 回放**：将真实请求复制给新版本执行。

# 四、常见线上问题及排查方法

## 问题一：Step 数过高

### 常见原因

- Agent 反复调用同一个检索工具；
- 规划不清晰；
- Tool Description 含糊；
- 没有停止条件；
- 检索质量差，始终找不到目标；
- 工具返回信息不足，导致重复尝试。

### 排查方式

先查看 Trace，确认是否出现：

```text
检索 → 未找到 → 再检索 → 未找到 → 再检索……
```

### 优化方法

- 优化 Prompt；
- 改进 Tool Description；
- 增加 Stop Condition；
- 设置 Step Budget；
- 提高检索召回和排序质量；
- 限制同一工具的重复调用次数。

## 问题二：延迟长尾严重

延迟长尾严重，通常指大多数请求很快，但少部分请求特别慢，导致 P95 或 P99 明显偏高。

### 常见原因

- 请求排队；
- 外部工具响应不稳定；
- 个别检索或 Rerank 请求很慢；
- 重试次数过多；
- 审批等待时间过长；
- 长上下文推理；
- Agent Step 数失控。

### 优化方法

- 根据延迟瀑布图定位瓶颈；
- 优化队列和并发策略；
- 缩短外部依赖超时时间；
- 增加熔断与降级；
- 限制 Step、Token 和 Timeout Budget；
- 对慢请求进行单独分析。

## 问题三：安全事件增多

### 常见原因

- 审批 Span 缺失；
- 某类工具调用没有触发 Policy Check；
- 权限范围设置过大；
- 不可信内容被当成高优先级指令；
- 参数或输出未经过校验；
- 第三方工具未经过安全复审。

### 排查重点

安全事件增加通常不只是 Prompt 问题，还可能代表治理层、权限层或执行层出现缺口。

## 问题四：成本上升

### 常见原因

- 工具重复调用；
- 上下文长度快速增长；
- 重复推理；
- 失败后不断重试；
- 所有任务都使用重型模型；
- 高成本 Rerank 被频繁触发。

### 优化方法

- 上下文裁剪；
- 更严格的 Tool Gate；
- 模型路由；
- 缓存；
- 并发或批处理；
- 减少重复检索和重复推理；
- 以“每成功任务成本”作为核心指标。

## 可观测性最佳实践

1. 从项目第一天开始设计 Trace Schema；
2. 保证所有版本都可以被观测和追踪；
3. 将 Trace 与 Eval 结果绑定；
4. 对观测字段进行脱敏和权限分层；
5. 每个 Dashboard 指标都应对应明确动作；
6. 异常指标应能够触发告警、阻断发布、回滚或纳入回归集。

# 五、Agent 安全风险与分层防御

## 1. Prompt Injection

Prompt Injection 指攻击者把恶意指令藏在用户输入、网页、文档、邮件或第三方数据中，试图影响模型的行为。

危险之处在于：

> 被带偏的模型不仅可能生成错误文本，还可能进一步驱动具有真实能力的工具和系统。

### 防御原则

1. 用户输入、网页内容和外部文档都应被视为不可信数据；
2. 不应将不可信数据直接并入高优先级系统指令；
3. 节点之间尽量使用结构化输出和 Schema 校验；
4. 对工具实行最小权限设计；
5. 危险操作加入审批或强确认；
6. 在执行环境中限制网络、文件和系统权限；
7. 将安全事件、工具调用和审批过程纳入 Trace 与审计。

## 2. Jailbreak

Jailbreak 通常翻译为“越狱”，指用户通过特殊话术诱导模型绕过原本的安全规则，输出本不应该提供的内容。

## 3. Tool Poisoning

Tool Poisoning 指第三方工具、工具描述或外部内容中包含误导性指令，使模型将其错误地当作可信指令，从而执行错误或危险操作。

## 4. Insecure Output Handling

Insecure Output Handling 指系统未经校验，就把模型生成内容直接交给下游系统执行。

例如：

- 直接执行模型生成的 SQL；
- 直接运行模型生成的 Shell 命令；
- 直接把模型生成内容写入网页；
- 未校验参数就调用支付或删除工具。

## 5. 为什么 Agent 比普通对话模型更危险

因为 Agent：

- 具有真实行动能力；
- 会主动读取网页、文档和邮件等不可信内容；
- 往往连接高权限工具和环境；
- 错误会随着多步执行不断传播；
- 风险可能隐藏在较长的调用链中，不容易被用户直接发现。

## 6. 分层防御机制

推荐建立以下八层防御：

1. 明确可信边界；
2. 数据与指令分离；
3. 工具最小化与能力最小化；
4. 参数与输出校验；
5. 高风险动作审批与二次确认；
6. 执行环境隔离与沙箱；
7. 监控与审计；
8. 红队测试与持续维护对抗集。

# 六、权限、审批、审计与治理

可以用四个关键词理解 Agent 安全体系：

> **权限 → 审批 → 审计 → 治理**

## 1. 权限

权限决定 Agent 能做什么、不能做什么。

权限模型的核心要素包括：

- **主体（Subject）**：谁在执行；
- **资源（Resource）**：操作什么对象；
- **动作（Action）**：执行什么操作；
- **上下文（Context）**：在什么条件下执行。

授权不能只依赖 Prompt 中的一句“你不能访问某类数据”。

更可靠的做法是：

- 连接建立时绑定真实身份；
- Token Scope 清晰且最小化；
- 服务端再次执行权限校验；
- 高风险 Server 不默认信任调用方；
- 不同租户和用户的数据相互隔离。

MCP 将工具调用标准化，但也要求系统更加严肃地处理授权和信任链。

## 2. 审批

审批用于在高风险动作真正执行前，增加人工或策略确认。

适合审批的操作包括：

- 支付；
- 删除数据；
- 发送外部邮件；
- 修改生产环境；
- 对外发布；
- 执行高权限命令。

## 3. 审计

审计需要回答：

> 这件事发生之后，是否可以被完整追溯？

审计信息通常包括：

- 谁发起了请求；
- 使用了哪个 Agent 和版本；
- 调用了哪些工具；
- 参数是什么；
- 谁批准了操作；
- 返回结果是什么；
- 是否发生重试、回滚或异常。

## 4. 治理

治理是组织层面的长期运行机制，包括：

- 权限模型设计；
- 审批策略设计；
- 审计要求；
- 安全评测；
- 红队测试；
- 第三方工具管理；
- 事故复盘；
- 责任分工。

## 5. 组织级治理框架

### 第一层：策略层

定义：

- 什么可以做；
- 什么不能做；
- 哪些操作需要审批；
- 哪些行为必须审计；
- 哪些代码只能在 Sandbox 中运行。

### 第二层：实现层

将策略落地为具体系统能力，例如：

- Policy Engine；
- Access Token Scope；
- 权限校验；
- Schema 校验；
- Tool Gate；
- 沙箱隔离；
- 审批工作流。

### 第三层：运营层

定期执行：

- Agent 评测；
- 安全红队；
- 事故复盘；
- 权限审查；
- 第三方工具复审；
- Prompt、Model 和 Tool Review。

### 第四层：责任层

明确谁负责：

- 策略制定；
- 系统实现；
- 日常运营；
- 安全响应；
- 上线审批；
- 事故处理。

# 七、成本、延迟与稳定性优化

> Agent 优化不能只关注单个 Token 的价格，而应同时考虑每成功任务的总成本、端到端延迟，以及失败和重试带来的放大效应。

## 1. 成本

Agent 成本可能包括：

- 输入 Token；
- 输出 Token；
- 长上下文成本；
- 检索成本；
- Embedding 成本；
- Rerank 成本；
- 工具调用成本；
- 失败重试成本；
- 人工审批成本。

最值得关注的不是“单次调用成本”，而是：

> **每成功任务成本 = 总成本 ÷ 成功完成的任务数**

如果一个便宜模型需要多次重试才能完成任务，最终成本可能高于一次使用更合适的模型。

## 2. 延迟

端到端延迟不仅是模型生成时间，还可能包括：

- 请求排队；
- 模型决策；
- 检索；
- Rerank；
- 工具执行；
- 网络等待；
- 审批确认；
- 重试；
- 最终生成与返回。

### 延迟瀑布图

```text
请求进入
→ 排队
→ 模型决策
→ 检索与 Rerank
→ Tool Use
→ 审批或确认
→ 最终生成
→ 返回用户
```

优化延迟时，应先通过 Trace 或瀑布图定位最慢的环节，而不是只盯着模型推理时间。

## 3. 稳定性

稳定性是指系统在流量变化、外部服务波动和错误出现时，是否仍能保持可控运行。

主要包括：

- Rate Limit 抗压；
- 工具失败处理；
- Retry；
- Timeout；
- Fallback；
- 熔断；
- Fail-Fast；
- 灰度发布；
- 快速回滚。

## 4. 常用优化杠杆

### 模型路由

根据任务难度使用不同模型：

- 简单分类、抽取任务使用轻量模型；
- 复杂规划和关键判断使用重型模型；
- 高风险任务可增加 Judge 或人工审批。

### 上下文优化

- 裁剪无关历史；
- 对长文档进行摘要；
- 引用相关片段，而不是塞入全文；
- 避免重复注入同一信息；
- 控制 Memory 和 RAG 内容规模。

### 缓存

缓存需要同时考虑：

- 数据时效性；
- 用户和租户隔离；
- 权限上下文；
- 缓存失效策略；
- 是否包含敏感信息。

### 并发、并行与批处理

适合将相互独立的任务并行执行，但应避免：

- 多个步骤争抢同一资源；
- 产生顺序依赖错误；
- 并发放大外部服务压力；
- 重复调用同一工具。

### Budget 控制

需要设置：

- Step Budget；
- Token Budget；
- Timeout Budget；
- 重试次数上限；
- 单工具调用上限。

### 幂等、重试与熔断

- 可重试操作应尽量具备幂等性；
- 重试应有次数上限和退避策略；
- 外部依赖持续失败时应触发熔断；
- 无法安全重试的操作应使用补偿机制或人工介入。

### SSE

SSE 主要改善用户的等待体验，让用户实时看到 Agent 当前步骤，但它不一定真正减少系统总延迟。

## 5. 不同 Agent 的优化重点

### RAG Agent

重点包括：

- 控制上下文膨胀；
- 提高检索命中率；
- 减少重复检索；
- 引用相关片段而非全文；
- 对长文档进行摘要；
- 只在必要时触发高成本 Rerank。

### Code Agent

重点包括：

- 减少无效工具调用；
- 只在关键步骤使用重型模型；
- 缩小 Repository 观察窗口；
- 先定位相关文件，再读取上下文；
- 控制命令执行和测试范围。

### Workflow Agent

重点包括：

- 明确 Fail-Fast 条件；
- 设计 Fallback 策略；
- 控制重试次数；
- 确保有副作用的步骤具备幂等或补偿机制；
- 保存任务状态，支持恢复与审计。

# 八、灰度发布、版本管理与回滚

## 1. 为什么 Agent 需要灰度发布

Agent 是一个由多种资产协同工作的系统，包括：

- 代码；
- 模型；
- Prompt；
- Tool；
- 知识库；
- Workflow；
- 权限策略；
- 评测集。

因此，发布与回滚不能只围绕代码版本设计，而要围绕全部资产统一管理。

Agent 特别需要灰度发布，原因包括：

1. Agent 行为具有一定非确定性；
2. 线上真实分布与离线数据集并不完全一致；
3. 风险可以按照用户、租户和场景分层控制；
4. Agent 问题经常不是“彻底不可用”，而是悄悄变差。

## 2. 推荐上线梯度

```text
本地开发环境
→ 离线评测
→ Shadow / Replay
→ 内部灰度
→ 小流量 Canary
→ 分租户或分场景放量
→ 全量上线
→ 持续监控与必要时回滚
```

风险开放顺序可以参考：

```text
内部员工
→ 低风险租户
→ 只读任务
→ 高价值但低破坏性任务
→ 高风险写操作
```

## 3. Canary 阶段看什么

Canary 阶段不能只看任务成功率，还应关注：

- Step 数；
- 工具调用分布；
- P50、P95、P99 延迟；
- 每成功任务成本；
- 重试率；
- 超时率；
- Fallback 触发率；
- 安全事件；
- 人工审批率；
- 与 Baseline 的差异。

## 4. 什么必须被版本化

版本化是给系统资产分配明确版本号，以支持追踪、比较和回滚。

### 模型层

- Base Model Version；
- 模型路由配置；
- 推理参数。

### 行为层

- System Prompt；
- 子 Agent Prompt；
- Planner Prompt；
- Judge Prompt；
- Stop Condition；
- Workflow 配置。

### 工具层

- Tool Schema；
- Tool Description；
- 工具实现版本；
- 参数校验规则；
- Tool Gate 配置。

### 知识层

- 文档版本；
- 索引版本；
- Embedding Model；
- Rerank Model；
- 检索配置。

### 治理层

- 权限策略；
- Token Scope；
- 审批规则；
- Policy Engine 版本；
- 安全规则。

### 评测层

- 评测集版本；
- 评价器版本；
- 评分标准；
- Baseline；
- 发布门禁。

## 5. 回滚原则

出现以下情况时，应考虑立即停止放量或回滚：

- 核心任务成功率明显下降；
- 高风险 Case 失败；
- 出现越权调用；
- 每成功任务成本异常上涨；
- P95 或 P99 延迟显著恶化；
- Step 数异常增加；
- 某工具错误率快速上升；
- 安全事件或用户投诉增加。

回滚时必须能够明确恢复：

- 代码版本；
- Prompt 版本；
- 模型和路由配置；
- Tool Schema；
- 知识库与索引；
- 权限和审批策略。

# 九、完整生产闭环

可以将整套 Agent 生产体系总结为以下流程：

```text
1. 定义业务目标与任务边界
                ↓
2. 拆解 Agent 关键能力
                ↓
3. 构建核心、失败、边界与对抗数据集
                ↓
4. 使用规则、模型与人工评价器
                ↓
5. 建立 Baseline 与发布门禁
                ↓
6. 通过 Trace、Metric 和 Log 定位问题
                ↓
7. 进行成本、延迟、稳定性与安全优化
                ↓
8. Shadow、内部灰度与 Canary 发布
                ↓
9. 在线监控并抽取真实失败样本
                ↓
10. 失败样本回流离线回归集
                ↓
11. 修复、验证、重新灰度
```

## 一句话总结

> **高质量 Agent 评测不是只判断最终回答是否正确，而是对输入理解、规划、检索、工具调用、安全审批、成本、延迟和稳定性进行全链路评估，并通过在线与离线闭环持续改进。**
