## 1. 评估的核心目标

Agent 评估首先要回答三个问题：

1. **任务效果**：系统能否正确完成任务？
2. **系统性能**：系统执行效率是否符合要求？
3. **资源消耗**：系统运行成本是否可控？

因此，Agent 评估通常围绕三个核心指标展开：

| 评估维度 | Agent 核心指标 | 关注的问题 |
|---|---|---|
| 任务效果 | 成功率 | Agent 能否正确完成任务 |
| 系统性能 | 延迟 | Agent 响应是否足够快 |
| 资源消耗 | 成本 | 单次任务或批量请求的成本是否可控 |

> 一句话总结：任何系统都绕不开**效果、性能和成本**，对应到 Agent 中就是**成功率、延迟和成本**。

---

## 2. Agent 评估的主要挑战

Agent 评估比普通模型评估更复杂，主要原因包括：

- 任务复杂度高；
- 输出形式多样；
- 结果可能具有一定主观性；
- Agent 可能涉及多步骤推理和工具调用；
- 系统需要在持续迭代中反复评估。

因此，通常需要：

1. 构造专门的评估数据集；
2. 建立自动化评估流程；
3. 持续收集结果；
4. 根据评估结果迭代系统。

---

# 3. 三个核心指标

## 3.1 成功率

成功率是所有指标中最直接反映 Agent 能力的指标，也是判断 Agent 优化是否有效时最重要的参考标准。

### 成功率关注什么？

- Agent 是否完成了任务；
- 最终结果是否正确；
- 工具调用是否成功；
- 是否满足用户要求；
- 是否出现关键步骤遗漏。

### 基本理解

```text
成功率 = 成功完成的任务数 / 总任务数
```

例如：

- 总共评估 100 个任务；
- 其中 85 个任务正确完成；
- Agent 成功率为 85%。

> 成功率反映的是“Agent 最终有没有把事情做对”。

---

## 3.2 延迟

延迟表示 Agent 从接收请求到完成任务所需要的时间。

常见延迟指标包括：

- 平均延迟；
- p95 延迟；
- p99 延迟。

### 平均延迟

平均延迟表示所有请求耗时的平均值。

但平均值可能会掩盖少量非常慢的请求，因此在生产环境中，还需要关注 p95 和 p99 等尾延迟指标。

---

## 3.3 p95 延迟与 p99 延迟

p95 和 p99 属于**尾延迟（Tail Latency）**指标，主要用于观察少部分慢请求的用户体验。

### p95 延迟

> 95% 的请求都能在这个时间内完成，剩下 5% 的请求会更慢。

例如：

- API 一共处理 10,000 次请求；
- p95 延迟为 500 ms。

这表示：

- 9,500 次请求耗时不超过 500 ms；
- 500 次请求耗时超过 500 ms。

### p99 延迟

> 99% 的请求都能在这个时间内完成，只有 1% 的请求会更慢。

例如：

- p99 延迟为 2 秒。

这表示：

- 9,900 次请求耗时不超过 2 秒；
- 100 次请求耗时超过 2 秒。

### p95 与 p99 的区别

| 指标 | 关注范围 | 主要含义 |
|---|---|---|
| p95 | 最慢的 5% 请求 | 大部分用户的较差体验 |
| p99 | 最慢的 1% 请求 | 极端情况下的用户体验 |

例如，一个 Agent 的延迟指标为：

```text
平均延迟：800 ms
p95：2 s
p99：8 s
```

可以理解为：

- 大部分情况下响应较快；
- 约 5% 的用户可能明显感觉到慢；
- 约 1% 的用户可能感觉系统接近卡住。

> 一句话总结：平均延迟看整体速度，p95 和 p99 看长尾慢请求。

---

## 3.4 成本

成本用于衡量 Agent 完成任务所消耗的资源。

常见指标包括：

- 单次任务平均成本；
- 每千次请求成本。

### 单次任务平均成本

```text
单次任务平均成本 = 总成本 / 完成任务总数
```

### 每千次请求成本

```text
每千次请求成本 = 总成本 / 请求总数 × 1000
```

> 成本指标用于判断 Agent 是否具备大规模部署和持续运行的可行性。

# 4. 自动化评估

自动化评估可以减少人工评审成本，提高评估效率和一致性。

常见方式包括：

## 4.1 Benchmark

Benchmark 是一套固定的评估任务或测试集，用于比较不同 Agent、模型或版本的表现。

它可以用于评估：

- 任务成功率；
- 推理能力；
- 工具调用能力；
- 特定业务场景能力。

---

## 4.2 Synthetic Data

Synthetic Data 指人工或模型生成的合成数据。

它可以用于：

- 补充真实数据不足的问题；
- 构造边界场景；
- 构造失败场景；
- 构造不同难度的测试任务；
- 扩充评估数据集。

---

## 4.3 自动测评系统

自动测评系统通常用于自动执行以下流程：

```text
准备评估数据
    ↓
运行 Agent
    ↓
记录输出与执行过程
    ↓
计算成功率、延迟和成本
    ↓
生成评估结果
    ↓
支持版本比较与持续迭代
```

> 自动评估的目标不是只跑一次测试，而是让评估能够持续执行，并接入 Agent 的开发迭代流程。

---

# 5. A/B Test

A/B Test 用于评估不同版本的 Agent 在真实环境中的表现。

## 5.1 基本流程

### 第一步：划分版本

例如：

- A 版本：当前线上版本；
- B 版本：优化后的新版本。

### 第二步：分配流量

将一部分真实用户请求分配给 A 版本，另一部分分配给 B 版本。

### 第三步：对比指标

重点比较：

- 成功率；
- 平均延迟；
- p95 延迟；
- p99 延迟；
- 单次任务成本；
- 每千次请求成本。

---

## 5.2 A/B Test 可以评估什么？

A/B Test 常用于判断以下改动是否有效：

- Prompt 优化；
- Model 版本升级；
- 工具调用策略优化；
- Agent 流程调整；
- 系统性能优化。

---

## 5.3 不能只看指标变化

在 A/B Test 中，不能只看到某个指标上升或下降，就直接判断新版本更好。

还需要考虑：

- 测试样本量是否足够；
- 流量分配是否合理；
- 不同版本面对的请求是否具有可比性；
- 指标变化是否具有统计显著性。

### 统计显著性的作用

统计显著性用于判断：

> 当前观察到的指标差异，是由版本改动带来的，还是由随机波动造成的。

例如：

- A 版本成功率为 80%；
- B 版本成功率为 81%。

虽然 B 版本看起来更高，但如果样本量很小，这 1% 的差异可能只是随机波动。

因此，A/B Test 不仅要看“指标有没有变化”，还要看“变化是否可信”。

---

# 6. 持续评估与系统迭代

Agent 评估不是一次性工作，而是一个持续循环。

推荐的迭代流程如下：

```text
构造评估数据集
    ↓
建立当前版本 Baseline
    ↓
修改 Prompt、模型或工具策略
    ↓
运行自动评估
    ↓
比较成功率、延迟和成本
    ↓
进行 A/B Test
    ↓
判断差异是否具有统计显著性
    ↓
上线或继续优化
```

# 7. 快速复习

## Agent 评估的三个核心指标

| 指标 | 回答的问题 |
|---|---|
| 成功率 | Agent 是否把任务做对 |
| 延迟 | Agent 完成任务是否足够快 |
| 成本 | Agent 完成任务是否足够经济 |

## 常见评估方式

| 方式 | 作用 |
|---|---|
| Benchmark | 在固定任务集上比较能力 |
| Synthetic Data | 补充边界、异常和复杂场景 |
| 自动测评系统 | 自动执行任务并统计指标 |
| A/B Test | 比较不同版本在线上真实环境中的表现 |

## p95 与 p99

- **p95**：95% 的请求能够在该时间内完成；
- **p99**：99% 的请求能够在该时间内完成；
- p99 比 p95 更关注极端慢请求。

---

# 8. 最终总结

Agent 评估体系的核心不是只看模型回答得好不好，而是综合判断：

1. **任务是否完成正确**；
2. **系统响应是否足够快**；
3. **运行成本是否可控**；
4. **新版本是否真的优于旧版本**；
5. **评估结果能否持续接入开发迭代流程**。

> 最终可以将 Agent 评估概括为：以成功率、延迟和成本为核心指标，以 Benchmark、合成数据、自动测评和 A/B Test 为主要手段，通过持续评估推动系统迭代。
