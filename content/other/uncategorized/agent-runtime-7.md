## 一、可靠执行：重试、幂等与补偿

### 1. 重试必须与幂等配合

重试不能单独使用，尤其是调用具有副作用的工具时。

如果一次操作已经执行成功，但系统因为网络或超时没有收到结果，再次重试可能造成：

- 重复扣款；
- 重复发消息；
- 重复创建订单；
- 重复写入数据。

因此：

- **重试**：解决暂时性故障；
- **幂等**：保证同一个请求重复执行时，不会产生重复副作用。

> 对副作用型工具，应先设计幂等机制，再允许自动重试。

### 2. 适合重试的情况

通常可以重试的情况包括：

- 网络问题；
- 短时间超时；
- 临时限流；
- 服务暂时不可用；
- 消息没有成功发出。

参数错误、权限不足、业务规则不允许等确定性错误，不应盲目重试。

### 3. 很多操作需要补偿，而不是回滚

部分业务操作无法真正回滚。例如已经完成支付后，通常需要通过退款这一反向操作进行补偿，而不是直接抹去原支付记录。

常见思路：

```text
原操作已经执行或部分执行
          ↓
执行对应的反向操作
          ↓
让业务恢复到可接受状态
```

例如：

- 已扣款 → 退款；
- 已创建订单 → 取消订单；
- 已占用库存 → 释放库存。

### 4. 幂等不只是“查一下数据库”

幂等的核心是：

> 同一个业务请求执行一次或多次，最终业务结果保持一致。

系统除了查询数据库，还要识别并处理不同状态，例如：

| 状态 | 含义 |
|---|---|
| `PENDING` | 等待处理 |
| `PROCESSING` | 正在处理 |
| `SUCCEEDED` | 已成功 |
| `FAILED` | 已失败 |
| `UNKNOWN` | 结果未知，需要进一步确认 |

最麻烦的情况是：操作可能已经成功，但系统没有收到响应。此时不能直接重试，否则可能产生重复副作用。

## 二、异步、流式、取消与恢复

### 1. 异步与流式的区别

- **异步（Asynchronous）**：描述任务如何执行，调用方不必一直阻塞等待。
- **流式（Streaming）**：描述执行结果如何反馈，系统可以持续返回中间结果。

> **异步是执行方式，流式是反馈方式。**

二者可以独立存在，也可以组合使用。

### 2. Cancel 与 Resume

系统要支持取消和恢复任务，需要持久化保存：

- `task_id`；
- 当前状态；
- 已完成步骤；
- Checkpoint；
- Artifact；
- 必要的上下文与输入参数。

取消时，系统需要知道任务执行到了哪里；恢复时，应尽量从最近的安全检查点继续，而不是从头重复执行。

## 三、Agent Runtime

### 1. Runtime 包含什么

Agent Runtime 不只是 Workflow，还通常包含：

- Workflow 编排；
- 上下文管理；
- 状态与 Checkpoint 管理；
- Artifact 管理；
- Trace；
- 多租户隔离（Multi-tenancy）；
- 工具注册与调用；
- 权限、审批和策略控制；
- 重试、取消、恢复与补偿。

### 2. 为什么需要 Runtime

模型输出具有自由度，但业务系统要求动作可控、可审计、可恢复。

Runtime 的作用是把模型的自由输出转换成受控动作：

```text
模型选择动作或工具
        ↓
Runtime 校验参数、权限与策略
        ↓
执行工具并记录状态
        ↓
返回结果、Artifact 与 Trace
```

### 3. 模型与应用层的职责边界

模型主要负责：

- 选择哪个 Tool；
- 填写 Tool 参数；
- 根据上下文决定下一步动作。

应用层或 Runtime 主要负责：

- 参数校验；
- 身份、租户与权限校验；
- 工具可见性控制；
- 工具的实际执行；
- 超时、重试与补偿；
- 状态、Artifact 与 Trace 保存；
- 审批、安全与审计。

> 模型负责“选择做什么”，系统负责“如何安全地完成”。

## 四、Structured Outputs、Function Calling 与 JSON Mode

### 1. Tool Schema

Tool Schema 通常通过以下信息帮助模型选择工具：

- `name`：工具名称；
- `description`：工具用途和适用场景；
- `schema`：参数名称、类型、必填项和约束。

模型会结合这些信息，选择正确的工具并生成对应参数。

### 2. 三者区别

| 能力 | 主要作用 |
|---|---|
| JSON Mode | 保证输出形式为 JSON，但不一定严格符合业务 Schema |
| Structured Outputs | 约束输出严格符合指定结构 |
| Function Calling | 将模型输出表达为工具名称和参数，交给应用执行 |

当前条件下，很多场景使用以下组合即可：

```text
Function Calling + 统一的 Tool Registry
```

### 3. Trade-off

`Trade-off` 指**权衡与取舍**。

系统设计通常需要在成本、速度、稳定性、安全性和复杂度之间做选择，而不是追求所有指标同时最优。

## 五、MCP 与工具服务

### 1. stdio Server 注意事项

在使用 `stdio` 的 MCP Server 中，不要向 `stdout` 输出普通日志。

原因是 `stdout` 通常用于传输协议消息，普通日志可能污染协议流，导致客户端解析失败。

建议：

- 协议消息写入 `stdout`；
- 普通日志写入 `stderr` 或独立日志文件。

### 2. 常见运行模式

MCP 或工具服务可以分为：

1. **本地开发者模式**：工具运行在本地，适合开发和调试；
2. **远程服务模式**：工具部署在远程服务器；
3. **网关代理模式**：通过统一网关管理鉴权、路由、限流和审计。

### 3. SDK 与分层

`SDK` 是 Software Development Kit，即**软件开发工具包**。

系统规模扩大后，应采用 Tiering（分层）思路，将协议、能力注册、执行、状态和观测等职责拆开。

### 4. Manifest

`Manifest` 常见含义：

- 清单文件；
- 资产清单；
- 声明文件。

它通常用于声明资源、能力、依赖、版本或配置信息。

## 六、Correlation ID

### 1. 中文翻译

`Correlation ID` 通常翻译为：

- **关联 ID**；
- **链路关联标识**；
- **请求追踪 ID**。

### 2. 定义

> 给一次完整请求分配的唯一编号。请求经过多个服务、Agent 和工具时，各环节产生的日志都携带这个编号，从而能够被串联起来。

### 3. 示例

```text
用户请求
  correlation_id = req-001
        ↓
Agent 编排
  correlation_id = req-001
        ↓
工具 / 数据库 / 外部服务
  correlation_id = req-001
        ↓
日志系统聚合完整调用链路
```

Correlation ID 可以帮助排查：

- 请求在哪一步失败；
- 哪个工具耗时过长；
- 是否发生重复调用；
- 一次任务经过了哪些服务和步骤。

## 七、Agent Runtime 分层

设计 Agent Runtime 时，可以先按职责分层：

```text
入口层
  ↓
编排核心
  ↓
能力注册层
  ↓
状态层
  ↓
执行层
  ↓
策略层
  ↓
观测层
```

### 1. 入口层

负责输入规范化，包括：

- 身份识别；
- 会话绑定；
- 租户绑定；
- 参数校验；
- 接口限制；
- 路由准备。

### 2. 编排核心

负责：

- 任务拆解；
- Workflow 执行；
- 步骤顺序；
- 分支、循环和停止条件；
- 模型、工具和人工审批之间的协调。

### 3. 能力注册层

负责管理：

- Tool Registry；
- Tool Schema；
- Namespace；
- 工具版本与可见范围。

### 4. 状态层

负责保存：

- Task 与 Step 状态；
- Checkpoint；
- Memory；
- Artifact；
- 幂等记录；
- 取消与恢复所需信息。

### 5. 执行层

负责：

- 模型调用；
- 工具调用；
- 超时控制；
- 重试与并发控制；
- 沙箱执行；
- 补偿操作。

### 6. 策略层

负责：

- 权限与安全策略；
- 审批策略；
- 成本预算；
- 模型和工具路由；
- 多租户隔离规则。

### 7. 观测层

负责记录：

- Log；
- Metric；
- Trace；
- Token 与成本；
- Latency；
- 工具调用成功率；
- 错误类型。

### 8. 上下文装配

Runtime 还需要决定每次模型调用能够看到什么内容，包括：

- 会话历史；
- Memory；
- RAG 检索结果；
- 可见的 Tool 与 Namespace；
- 审批与系统策略；
- Artifact 摘要；
- 当前任务状态。

上下文不是越多越好，需要在信息完整性、Token 成本、响应速度和噪声之间进行权衡。

## 八、常见术语

### CRM

`CRM` 是 Customer Relationship Management，即**客户关系管理**。

它是企业用来统一管理客户信息和跟进过程的工具，通常包括：

- 客户资料；
- 销售线索；
- 跟进记录；
- 商机阶段；
- 合同、订单和售后信息。

---

## 总结

> Agent Runtime 的本质，是在模型与真实业务系统之间增加一个受控执行层，使模型的决策能够被校验、追踪、恢复、审计并安全落地。
